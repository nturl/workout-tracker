behavior; the entire signed-in live app was not exercised in a real browser
in this run. This draft merges all seven lane reports into one ranked ledger,
deduping findings that share a root cause and cross-referencing findings that
are related but distinct.

## BUG-01  Server `deepMerge` is last-write-wins per leaf/scalar — erases completions, tri-state habit marks, and reverts `level` on a concurrent/stale push
Severity: P0 data loss
Area: A/E
Status: VERIFIED (test)
Lane id: A1, A2, E4
Where: `src/app/api/sync/route.ts:92-102` (`deepMerge`), used at `src/app/api/sync/route.ts:117` and `:82`.
Repro: three concrete sequences, all against the same code path:
1. **Completions (A1)**: Device A pushes `{ completions: { "k": true } }` after completing a set. Device B's debounced sync then pushes its own stale full snapshot, `{ completions: { "k": false } }`, taken before A's push landed. GET the stored blob: `completions["k"]` is `false` — B's stale push silently erases A's real completion.
2. **Tri-state habits (A2)**: Device A explicitly marks a habit **missed** today (`{ habits: { meditation: { "2026-09-01": false } } }`). Device B, unaware, pushes its stale full state where that day is still `true`. GET: the day is `true` again — B's stale push silently un-misses the day.
3. **`level` (E4)**: Device A (session 5+ min old, never refetched) still has `level: "intermediate"` cached. Device B pushes `level: "advanced"`. Device A's next unrelated push (e.g. a habit toggle, since `getSyncPayload()` always sends the full current store) includes the stale `level: "intermediate"` and reverts B's `"advanced"` on the server.
Expected: a later, real value from one device should not be silently reverted by an older, stale push from another device, for any of `completions`, `habits`, or `level`.
Actual: whichever push is processed last by the server wins every key it includes, even a stale one — because every debounced push (`useSync.ts` `getSyncPayload()`) sends the client's entire current state, not a diff, and `deepMerge` does a plain `result[k] = v` overwrite at every leaf/scalar with no timestamp, version, or conflict-aware handling.
Root cause: `deepMerge` recurses into nested objects but overwrites leaves and top-level scalars unconditionally. The store's own code comments (`mergeCompletionsPreferTrue`, "V19 P0: … Guards against the regression that ate a full workout today") show this exact race was already hit once and fixed — but only on the client's hydrate-down path. The server's own persisted copy, which every device eventually re-hydrates from, has no equivalent protection, and `level` (the only bare top-level scalar field) gets the same unversioned overwrite treatment as `completions`/`habits` leaves.
Evidence: `src/__tests__/bugs/lane-a.test.ts` tests `BUG-A1`, `BUG-A2` (`it.fails`); `src/__tests__/bugs/lane-e.test.ts` test `BUG-E4` (`it.fails`). Un-wrapped runs confirmed on HEAD: `AssertionError: expected true to be false` (A1, A2) and the E4 assertion failing identically for `level`.
Proposed fix: give the server a conflict-aware merge rule for `completions`/`habits` leaves (matching the client's existing prefer-true guard, extended correctly for the tri-state case) and either a dirtiness flag or CAS/version treatment for `level`, instead of blind last-write-wins on any of them. This is a behavior change to `deepMerge` and the sync payload contract, not a pure bugfix — needs review as a storage/merge-semantics change, and may warrant a migration note for `level`.

## BUG-02  `mergeHabitDefs` discards a dirty (unacked) local habit-list edit whenever any strictly-newer server version arrives
Severity: P0 data loss
Area: B
Status: VERIFIED (test)
Lane id: B1
Related: BUG-I2 (same function, different branch, INFERRED)
Where: `src/hooks/useWorkoutStore.ts:90-100` (`mergeHabitDefs`), called from `hydrateFromSync` at `:433-441`; edit actions that set `habitDefsDirty: true` without bumping `habitDefsVersion`: `addHabit` (`:312-327`), `renameHabit` (`:329-337`), `removeHabit` (`:339-350`), `moveHabit` (`:352-361`).
Repro:
1. Local store is at `habitDefsVersion: 4`; the user renames a habit, setting `habitDefsDirty: true` but leaving `habitDefsVersion` at 4 (version is server-assigned only, per the file's own doc comment at lines 66-67).
2. Before that edit is pushed/acked, `hydrateFromSync` runs again with a `serverData` snapshot at `habitDefsVersion: 5` that does not contain the edit — realistically triggered by BUG-06's duplicate `useSync` instance re-hydrating on every Settings-tab open.
3. In `mergeHabitDefs`: `const serverWins = localEmpty || serverV > localV || (!local.habitDefsDirty && serverV === localV && JSON.stringify(incoming.habitDefs) > JSON.stringify(local.habitDefs));` — `serverV > localV` (5 > 4) is `true` unconditionally; `habitDefsDirty` only gates the equal-version tiebreaker on the third line, never this branch.
Expected: a dirty local edit should not be replaced by server data until that specific edit has been acked.
Actual: any strictly-newer server version wins outright, dirty or not, and `habitDefsDirty` is reset to `false` in the process — so the edit isn't just overwritten in the UI, it stops being tracked as "needs to be re-sent" and is gone for good.
Root cause: the dirty-guard was written to protect only the deterministic equal-version tiebreaker branch and was never extended to the "strictly newer version" branch, even though a locally dirty edit's version doesn't change until acked.
Evidence: `src/__tests__/bugs/lane-b.test.tsx`, test `BUG-B1` (`it.fails`) — confirms `out.habitDefs` equals the stale server copy `B`, not the local dirty edit `A`.
Proposed fix: gate the `serverV > localV` branch on `!local.habitDefsDirty` too (or track the version each dirty edit was based on and only adopt server data newer than that base, deferring adoption until the in-flight push resolves). Touches the sync/version-merge contract in `mergeHabitDefs` and the ack-reconciliation path.

## BUG-03  Un-scoped, un-cleared local store leaks a previous account's data into a newly signed-in account's server record
Severity: P0 data loss (cross-account contamination)
Area: E
Status: VERIFIED (test)
Lane id: E1
Where: `src/hooks/useWorkoutStore.ts:468-486` (`persist(..., { name: "workout-store" })` — one fixed localStorage key, no account id); `src/hooks/useSync.ts:63-79` (hydrate-then-push-back on first `serverData`); `src/hooks/useWorkoutStore.ts:380-459` (`hydrateFromSync` merges local into server additively, never clears); `:461-466` (`getSyncPayload` sends the entire current store unconditionally).
Repro:
1. Account A signs in on a device, taps a completion and saves a log entry — pushed to `user:A:data` and persisted forever under the single `workout-store` localStorage key (no account id in the key).
2. Account A signs out; Account B signs in on the same device/tab.
3. `useSync(true)` runs for account B; GET `/api/sync` returns account B's own (empty) data.
4. `hydrateFromSync` merges the leftover local state (still account A's data, never reset) into the store.
5. `pushSync(getSyncPayload())` immediately POSTs that merged store — including account A's data — to `user:B:data`.
Expected: Account B's server record should only ever contain data Account B entered.
Actual: Account A's completion and log entry are present in Account B's server record.
Root cause: the zustand store has no "current account" concept; the persisted key is a single global string, and the sync hook trusts and forwards whatever the store currently holds the moment a different account authenticates, with no reset/clear step keyed to account changes.
Evidence: `src/__tests__/bugs/lane-e.test.ts` — `BUG-E1` (`it.fails`), reproducing steps 1-5 against the real store singleton and the real `/api/sync` route with a mock Redis.
Proposed fix: scope the persisted localStorage key by the signed-in Clerk user id (e.g. `workout-store:${userId}`, clean/anonymous key when signed out) and reset the in-memory store whenever the authenticated user id changes, before any hydrate/push runs. Touches the persist config's `name` — schema/migration-relevant for existing installs.

## BUG-04  `exerciseLogs[].completedAt` is silently stripped by the sync validator on every round trip
Severity: P0 data loss (silent, on a documented feature field)
Area: E
Status: VERIFIED (test)
Lane id: E3
Where: `src/types/workout.ts:6-15` (`ExerciseLog.completedAt?: string`, documented as powering timing-history views); `src/lib/validators.ts:3-10` (`exerciseLogSchema` — plain `z.object({...})` with no `completedAt` field and no `.passthrough()`, unlike `recoveryEntrySchema` at `:59`); `src/app/api/sync/route.ts:72` (`syncBodySchema.safeParse(body)` on every POST, persisting the stripped `parsed.data`).

2. `getSyncPayload()` sends it verbatim in the POST body.
3. `syncBodySchema.safeParse` parses successfully but drops the unrecognized `completedAt` key (Zod v4 `z.object()` strips unrecognized keys by default).

## BUG-05  Client-side `mergeDailyHabit` still uses the pre-tri-state prefer-true rule, so an explicit local "missed" can be overwritten by a hydrate
Severity: P1 wrong behaviour user will hit
Area: A
Status: VERIFIED (test)
Lane id: A3
Where: `src/hooks/useWorkoutStore.ts:402-410` (`mergeDailyHabit`, used inside `hydrateFromSync`).
Repro:
1. Local store: `habits.meditation["2026-09-01"] = false` (user tapped "missed" today).
2. `hydrateFromSync({ habits: { meditation: { "2026-09-01": true } } })` runs (e.g. the periodic re-hydrate effect in `useSync.ts:74-78`, or the very next GET after BUG-01's server-side clobber already turned the value back to `true`).
3. Read `useWorkoutStore.getState().habits.meditation["2026-09-01"]`.
Expected: stays `false`.
Actual: becomes `true`.
Root cause: `mergeDailyHabit` does `merged[date] = Boolean(merged[date]) || Boolean(value)` — the same prefer-true rule copy-pasted from `mergeCompletionsPreferTrue`. That rule is correct where `false` just means "not yet," but 989297d gave the habits map a third meaningful state (explicit miss) without updating this merge function.
Evidence: `src/__tests__/bugs/lane-a.test.ts`, test `BUG-A3` (`it.fails`): `AssertionError: expected true to be false`.
Proposed fix: only apply prefer-true when the local value is `undefined` (server can fill a gap, never override an explicit local `true` or `false`); a fully precise fix needs a per-entry timestamp, which is a real schema change and should be scoped separately.

## BUG-06  `HabitManager`/Settings and `WorkoutsTab` run two independent `useSync()` instances, causing an extra push+merge every time Settings is opened
Severity: P1 wrong behaviour user will hit
Area: B/E
Status: VERIFIED (trace)
Lane id: B2
Where: `src/app/page.tsx:32` (`useSync` instance passed into `WorkoutsTab`) vs. `src/components/tabs/SettingsTab.tsx:24` (its own separate `useSync` call); `HabitManager` (`src/components/settings/HabitManager.tsx:19`) only receives `SettingsTab`'s local `syncNow`. `SettingsTab` is unmounted/remounted on every tab switch (no `display:none` keep-alive, unlike `WorkoutsTab`).
Repro (trace, pinned by a source-check test): each `useSync()` call creates a fresh `hydrated` ref and a fresh `useMutation`. Every time Settings opens, a brand-new instance mounts with `hydrated.current === false`; its effect (`useSync.ts:63-79`) runs the `!hydrated.current` branch on the first `serverData` it sees — the already-cached react-query response (subject to 300s `staleTime`), not a fresh fetch — and unconditionally calls both `hydrateFromSync(serverData)` and `pushSync(getSyncPayload())`.
Expected: opening Settings should not by itself trigger a sync push; one `useSync` instance (or one owner of the "first load" push/hydrate) should be shared.
Actual: two independent `hydrated` flags, two independent debounce timers, two independent mutations, both driving the same global store — every Settings-tab open fires an extra, unnecessary full-state `POST /api/sync` and re-runs the merge in BUG-02 against a snapshot that can be up to 5 minutes stale.
Root cause: `useSync` was designed as a page-level singleton (comment at `useSync.ts:33`, "V14 bandwidth diet") but is instantiated per-consumer instead of lifted once and threaded down.
Evidence: `src/__tests__/bugs/lane-b.test.tsx`, `BUG-B3` (source-check, passing — confirms both files independently call `useSync(...)`).
Proposed fix: lift the single `useSync()` call to `page.tsx` (already done for `WorkoutsTab`) and pass `syncNow`/`syncStatus` into `SettingsTab`/`HabitManager` as props.

## BUG-07  A brand-new account's empty (`null`) server response never opens the auto-sync-on-change gate
Severity: P1 wrong behaviour user will hit
Area: E
Status: VERIFIED (test + trace)
Lane id: E2
Where: `src/hooks/useSync.ts:8-13` (`fetchSyncData` resolves `null`, not `undefined`, when the server has nothing — `src/app/api/sync/route.ts:49`); `useSync.ts:63-64` (`if (!serverData) return;` — `!null` is `true`, same early return as "query hasn't resolved yet"); `:29,67,70` (`hydrated.current` only set `true` inside that guarded block); `:114-115` (auto-push subscription gated on `hydrated.current`).
Repro:
1. A genuinely new account signs in with an empty local store.
2. GET `/api/sync` resolves and `fetchSyncData` returns `null`.
3. The hydrate effect sees `serverData === null` and returns before setting `hydrated.current = true`; it only re-runs when dependency identities change, which they won't just because time passes.
4. The user completes a workout/toggles a habit; the `subscribe` callback fires every time but `hydrated.current` is still `false`, so `debouncedPush()` never runs.
Expected: a new account's local changes sync automatically, same as an existing account's.
Actual: for a genuinely fresh account, auto-sync-on-change never activates for the life of the component mount; only the manual "sync now" button (which bypasses the `hydrated.current` check) ever pushes.
Root cause: the hook conflates "no serverData yet" (loading) with "serverData is legitimately empty" (new account) via a falsy check instead of distinguishing `undefined` from `null`.
Evidence: `src/__tests__/bugs/lane-e.test.ts` — `BUG-E2` (`it.fails`), reproducing the exact guard.
Proposed fix: track "has the initial GET resolved" separately from "did it return data" (e.g. react-query's `isSuccess`, or `serverData !== undefined`) so the hydrate effect sets `hydrated.current = true` even when the server legitimately has nothing yet.

## BUG-08  `CircuitTimer` never requests a screen wake lock
Severity: P1 wrong behaviour user will hit
Area: C
